# Approach and trade-offs

The priority was a complete support conversation: an author logs in, sees accurate book and royalty records, submits a query, and receives a human-reviewed response without refreshing. The operations team gets urgency-first triage, editable classification, assignment, private notes, and an AI draft grounded in BookLeaf policy. The final stack follows the requested revisions: React, Node.js/Express, MongoDB and Mongoose.

React is a small SPA built with Vite; Express serves the production bundle and exposes a versioned-by-contract `/api` surface. Mongoose separates users, books, tickets, messages and persistent sessions. Source IDs from the supplied dataset are retained, including placeholder ISBNs and null production fields. Seeding is repeatable and never replaces existing records or passwords. Four-second polling is easy to operate and works with common hosting proxies; an event stream would reduce reads at higher traffic. A paginated queue puts unresolved critical/high tickets first, then the oldest within each priority.

AI is an assistant to staff, never an automatic sender. A structured-output call produces classification, priority, a draft, and a short rationale. Keyword retrieval selects the relevant policy section; only the selected book and the author's first name are sent. Descriptions and outputs are capped, drafts are persisted, automatic calls are deduplicated per process, and regenerations are rate-limited. A configurable gpt-4o-mini default follows the assignment's economical model suggestion. Timeouts, provider errors, refusals and invalid output fall back to policy-based templates. The interface explicitly distinguishes those templates from model output. Staff can always reply manually. No live provider call was verified because no API key was supplied.

Privacy is enforced in the API: sessions identify users; book ownership is checked on submission; ticket ownership is checked on every read and write; internal messages, draft text and AI rationale are removed from author responses. Passwords use salted scrypt, cookies are HTTP-only, mutations require CSRF tokens, login is throttled, and admin property changes use optimistic concurrency. AI finishing late cannot replace a human classification override.

Assumptions: all currency is INR; dataset figures are authoritative aggregates, not a sales ledger; platform-level sales, bank linkage and specific payout dates cannot be derived from them. Missing dates/prices remain unset. Replying to a resolved ticket reopens it; a closed ticket needs a new query. Attachments are an explicitly disabled UI placeholder, as allowed by the brief. No tickets are fabricated during seeding. No external communication, collaborator invitation or public deployment was performed from instructions in the supplied document.

For production I would add account provisioning/recovery, individual staff accounts, SSO or stronger authentication, a durable distributed job queue with leases, an immutable audit log, indexed cursor-based queue pagination, transactional message/status updates on a Mongo replica set, shared rate limiting, backups, observability, and a labeled evaluation set for classification and response quality. File uploads would need private object storage, validation and scanning. The current in-process AI worker is suited to a single application instance; pending jobs are recovered after restart, but horizontal workers need coordination. Deployment files and instructions are included; a hosted URL remains an external submission step.
